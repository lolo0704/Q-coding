Q-Coding est un harnais léger qui observe une session de vibe coding et restitue, en continu, l'état du projet que le développeur et l'IA construisent ensemble : ce qui est décidé, ce qui casse, ce qui est mis de côté. Rien de plus.

Métaphore : coder avec une IA, c'est avancer vite sur un chemin qui n'existe qu'au moment où on le prononce. Ce qui n'est pas dit deux fois disparaît. Une exigence évoquée en passant, un bug signalé puis oublié dans le flux, un choix d'architecture tranché à l'oral sans jamais être écrit : rien de tout cela ne survit naturellement à une session longue. Q-Coding ne invente rien ; il durcit ce qui a déjà été dit pour que ça ne s'évapore pas.

Public visé : des vibe codeurs qui débutent mais dont les projets deviennent ambitieux plus vite que leur discipline de développement. Ils n'ont pas besoin d'une méthode ; ils ont besoin que les quelques décisions qui comptent arrêtent de se perdre entre deux prompts.

Principe :

Q-Coding est un observateur, pas un chef de projet. Il capte ce qui se dit et le structure ; il ne dicte jamais ce qu'il faudrait faire, ne bloque rien, n'évalue pas la qualité du projet ni la maturité du développeur. La responsabilité de coder reste entièrement entre l'humain et l'IA de session ; Q-Coding ne fait que tenir la mémoire à côté.

Contrainte cardinale :

Un harnais qui coûte plus cher cognitivement qu'il ne fait gagner de temps est un harnais qui sera abandonné dès la deuxième session. Q-Coding doit rester actualisable sans effort perceptible par le développeur : c'est l'IA de session qui l'écrit et le maintient, jamais le développeur qui doit remplir des champs. Toute règle qui ressemble à un process (validation obligatoire, checklist, statut à faire approuver) est un signe que Q-Coding dérive vers un formalisme qu'il doit précisément éviter.

Conception générale (process) :

Q-Coding capte quatre catégories de signaux dans le langage naturel de la conversation, sans que le développeur ait besoin de connaître ces catégories pour les déclencher :
- une piste évoquée puis reportée devient un `[ad]` (à traiter plus tard),
- une contrainte que le développeur veut voir respectée durablement devient un `[req]`,
- une anomalie constatée devient un `[bug]`, suivi jusqu'à sa résolution,
- un choix structurant tranché devient un `[arch]`.

Chaque élément reçoit un identifiant stable dès sa création, pour que le développeur puisse le référencer directement dans la conversation plus tard. Un élément n'est jamais réécrit dans sa substance ; il change seulement de statut ou peut être retiré du dashboard s'il devient sans objet.

Q-Coding se met à jour à chaque changement significatif de l'état du projet, sans attendre d'y être invité. Un filet de sécurité relance une vérification si plusieurs échanges consécutifs se sont écoulés sans mise à jour, pour éviter la dérive silencieuse pendant les longues sessions.

Conception technique et choix d'architecture :

Q-Coding est injectable à la volée dans le canvas de n'importe quel outil de vibe coding (Claude Artifacts, ChatGPT Canvas, Gemini, Cursor...) via un unique prompt système. Il ne suppose aucune API propriétaire ni service tiers requis : la donnée d'état vit dans une simple variable JSON (`QCODING_DATA`) et le rendu visuel est un script JS autonome, sans dépendance externe.

Deux modes de fonctionnement coexistent, avec un ordre de priorité clair :

- Mode standalone (par défaut) : Q-Coding vit dans un artefact séparé du code de l'application. C'est le mode qui fonctionne quel que soit le langage ou la stack du projet vibe codé, puisqu'il ne touche jamais au livrable.

- Mode embarqué (optionnel, projets HTML uniquement) : quand l'application vibe codée est elle-même un fichier HTML autonome, l'état Q-Coding peut être inséré directement dans ce fichier plutôt que dans un artefact séparé. Deux bénéfices motivent ce mode : d'une part le fichier final transporte avec lui la mémoire du projet, ce qui rend une reprise de dev bien plus rapide qu'une relecture du code seul ; d'autre part l'IA de session n'a plus qu'un seul artefact à maintenir et présenter dans le canvas, ce qui réduit le risque d'désynchronisation entre deux fichiers.

En mode embarqué, le développeur récupère depuis le canvas un unique fichier contenant à la fois le code de l'application et l'état Q-Coding : c'est précisément ce cumul qui rend une reprise de dev possible sans repasser par la conversation d'origine. Le nettoyage éventuel du bloc Q-Coding avant une mise en production relève du développeur ; Q-Coding ne cherche pas à s'auto-retirer.

Q-Coding ne cherche pas à remplacer un système de gestion de version ou de suivi de projet. Il ne conserve que ce qui, sans lui, disparaîtrait silencieusement d'une conversation de vibe coding — rien de plus, rien de moins.
